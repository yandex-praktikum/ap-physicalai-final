# Финальный проект Physical AI

В этом проекте вы пройдёте весь путь от обучения робота в симуляторе до модели,
которая управляет им по изображению с камеры. Сначала вы обучите RL-политику —
модель, которая выбирает действия и улучшает их по награде. Затем соберёте записи
её успешных действий и обучите на них другую модель методом Behavior Cloning (BC).
В конце проверите, как BC ведёт себя при изменениях сцены, и попробуете улучшить её.

## Что нужно получить

В проекте два робота: UR5e (`ur5e`) и KUKA iiwa 14 (`iiwa14`). Для каждого доступны
четыре задачи:

| ID задачи для команд | Что должен сделать робот |
|---|---|
| `cup_plate` | Перенести чашку в тарелку |
| `cup_shelf` | Поставить кружку на подставку |
| `cup_distractor` | Перенести первую кружку в тарелку, не сдвигая соседнюю |
| `color_match` | Выбрать из двух тарелок подходящую по цвету и поставить в неё кружку |

Из восьми доступных сочетаний **выберите одну пару «робот + задача»** и выполняйте
весь проект для неё. Нужно обучить RL-политику, собрать ею данные и получить три
варианта BC: по изображению, по изображению и состоянию робота, после обучения
с изменениями сцены. Работать с другими парами для сдачи не требуется.

В шаблоне уже готовы сцены, управление роботами, обучение PPO, сбор данных,
простой BC и запуск моделей для проверки. Ваша работа — обучить модели,
провести сравнения и объяснить результаты. Свои архитектуры и способы улучшения
можно выбирать самостоятельно.

Все команды ниже показаны для `ur5e/cup_plate`. Если выбрали другую пару,
замените в командах имя робота, ID задачи и каталоги результатов.

## 1. Познакомьтесь со сценами

Установите зависимости по [README](README.md) и выполните проверку запуска из него.
Откройте сцену выбранной пары командой просмотра. Например:

```bash
MUJOCO_GL=glfw python -m physical_ai.scene_tools --robot ur5e --task cup_plate
```

Если работаете на сервере без графического окна, сохраните изображение:

```bash
MUJOCO_GL=osmesa python -m physical_ai.scene_tools --robot ur5e --task cup_plate \
  --snapshot runs/scene.png
```

Изучите расположение предметов и цель каждой задачи. В [справочнике MuJoCo](MUJOCO_GUIDE.md)
показано, как посмотреть суставы и параметры объектов, получить их положение
и изменить сцену. Он понадобится при исследовании устойчивости моделей.

Один **эпизод** — попытка выполнить задачу от начального положения до успеха,
ошибки или окончания времени. В нём разрешено до 1000 действий. Робот получает
новую команду 20 раз в секунду. Команда состоит из четырёх чисел: движения захвата
по X, Y, Z и команды пальцев. Перевод этих команд в движения суставов уже реализован.

Чтобы попытка считалась успешной, предмет должен оказаться на нужном месте,
стоять вертикально и почти не двигаться. Робот должен отпустить его и отвести
захват. Эти условия должны сохраняться восемь шагов подряд; проверка автоматическая.
В задаче с соседней кружкой её смещение больше 2 см по столу завершает попытку
неудачей. В задаче цвета кружка может соответствовать любой из двух тарелок.

**Сохраните в отчёт:** краткое описание наблюдений, действий и условий успеха,
а также выбранную пару и причину её выбора.

## 2. Обучите RL-экспертов

RL-политика здесь получает точные данные симулятора о роботе, предметах и целях.
После обучения она будет экспертом, который показывает правильные действия для BC.
Поэтому сначала нужно убедиться, что эксперт достаточно часто решает задачу.

### Что уже настроено

Для первого запуска используйте `configs/ppo_calibrated.json` без изменений.
Это готовая последовательность обучения PPO, на которой получены работающие
эксперты. Вам не нужно самостоятельно придумывать эту последовательность.

В отличие от первой практики, здесь используется библиотека Stable Baselines3.
Алгоритм остаётся PPO, но команды и файлы сохранённых моделей отличаются.
Используйте настройки из этого проекта; переносить конфигурацию прежней практики
для первого запуска не требуется.

Обучение идёт от простого к сложному: сначала робот начинает попытку ближе
к завершению переноса, затем учится выполнять всё большую часть задачи.
Такой порядок называют **curriculum**. Начальные состояния уже предоставлены
в `assets/reset_states/` в формате LeRobot. Они получены с помощью контроллера
и используются только для начала попыток. Саму политику PPO обучает по награде;
действия контроллера не служат ответами для её обучения.

Кроме того, часть моделей начинает обучение с весов уже обученной модели другой
задачи или робота. Поддержка такого переноса, признаки расстояний до объектов,
ограничение резкости движений и настройки случайных действий при обучении уже
реализованы. Самостоятельно восстанавливать эти приёмы по прошлым практикам не нужно.
Укажите в отчёте, что воспользовались предоставленной помощью.

### Запуск и проверка

```bash
python -m physical_ai.train_curriculum --recipe configs/ppo_calibrated.json \
  --target ur5e/cup_plate --out runs/ppo
```

Скрипт запускает только стадии, необходимые для выбранного `--target`. В рецепт
могут входить промежуточные модели другой задачи или робота: они нужны для переноса
весов. Скрипт обучает их автоматически; отдельно собирать для них данные, обучать BC
или включать их в сдачу не нужно. При повторном запуске завершённые стадии будут
использованы снова. Не запускайте две команды с одним каталогом результатов
одновременно. Путь итоговой модели появится в `runs/ppo/outputs.json`.

После обучения проверьте модель на 50 полных эпизодах:

```bash
python -m physical_ai.evaluate --robot ur5e --task cup_plate --kind rl \
  --checkpoint runs/ppo/experts/ur5e/cup_plate/last.zip \
  --episodes 50 --seed 50000 --out runs/ur5e/cup_plate/rl_eval.json
```

Эта проверка начинает каждую попытку с обычного начального положения. Именно её
результат показывает, умеет ли робот выполнять задачу целиком. Успех в коротких
учебных попытках во время curriculum для этого недостаточен.

Параметр `seed` задаёт последовательность случайных начальных условий. Одинаковый
seed позволяет сравнивать модели в одинаковых условиях. Для итоговой проверки
выбирайте seeds, которые не использовали при обучении и подборе настроек.

В результате найдите `success_rate` — долю успешных попыток. Например, `0.8`
означает 40 успехов из 50. Перед сбором данных добейтесь **не менее 80%** для
выбранной пары. В задаче цвета проверьте также `by_goal_slot`: модель должна
достигать этого уровня отдельно для каждой из двух целевых тарелок.

Для выбранной пары сравните минимум два варианта настроек PPO. Например, измените
`learning_rate` — размер шага обновления весов — или `total_steps` — число действий,
на которых обучается стадия. Меняйте один фактор за раз, используйте копию JSON
и новый каталог `--out`. Укажите, какие стадии и значения вы изменили.

**Результат этапа:** выбранная RL-модель, настройки и логи обучения, таблица
успешности на полных эпизодах и сравнение двух вариантов настроек. Сохраняйте `.zip`
модели вместе с соседним `.json`: в нём записаны настройки и сведения о файле.

## 3. Соберите демонстрации в LeRobot

Демонстрация — запись одного эпизода: что модель видела и какое действие выбрала
на каждом шаге. Соберите демонстрации обученным RL-экспертом для выбранной пары.

Для начала используйте 100 успешных эпизодов для обучения и 20 для выбора модели:

```bash
python -m physical_ai.data --robot ur5e --task cup_plate \
  --checkpoint runs/ppo/experts/ur5e/cup_plate/last.zip \
  --out data/ur5e/cup_plate/train --episodes 100 --seed 1000 --max-attempts 500
python -m physical_ai.data --robot ur5e --task cup_plate \
  --checkpoint runs/ppo/experts/ur5e/cup_plate/last.zip \
  --out data/ur5e/cup_plate/val --episodes 20 --seed 10000 --max-attempts 100
```

`train` используется для обучения BC, `val` — для выбора сохранённой модели.
Сборщик сохраняет успешные эпизоды и останавливается, когда собрал нужное число
или исчерпал число попыток `--max-attempts`. Если успешных эпизодов мало, сначала
разберите ошибки эксперта. Числа 100/20 — начальный размер данных, а не гарантия
хорошего BC: при необходимости соберите больше и объясните своё решение.

Формат данных — **LeRobot v3**. Каждый каталог содержит числовые данные в `data/`,
видео в `videos/` и описание в `meta/`. Основные поля:

| Поле | Что в нём хранится |
|---|---|
| `observation.images.front` | Изображение с камеры, RGB 84×84 |
| `observation.state` | Положения и скорости суставов и пальцев |
| `action` | Четыре компоненты команды роботу |

Изображение и состояние записываются **перед** соответствующим действием.
В `meta/provenance.jsonl` сохранены seed, параметры сцены, успешность эпизода
и контрольная сумма файла эксперта — по ней можно проверить, какая модель
собрала данные. В `manifest.json` записаны попытки сбора. Сохраняйте и передавайте
каталог датасета целиком.

Обучающая и проверочная выборки должны состоять из разных эпизодов.
Не распределяйте соседние кадры одной попытки между `train` и `val`.
Для последующей проверки поведения BC используйте ещё одну, отдельную
последовательность начальных условий.

**Результат этапа:** данные LeRobot для выбранной пары с отдельными `train` и `val`.
В отчёте укажите число эпизодов и кадров, долю успешных попыток сбора и эксперта,
который использовался. Покажите несколько примеров записанных эпизодов.

## 4. Обучите BC и сравните результаты

BC учится предсказывать действия эксперта по собранным демонстрациям.
Сначала обучите простой вариант только по изображению — это **baseline**,
то есть исходная модель для сравнения. Затем добавьте состояние робота:
положения и скорости суставов и пальцев. Эти данные называют **проприоцепцией**.
Координаты предметов и целей из симулятора подавать BC нельзя.

```bash
python -m physical_ai.bc --train-dir data/ur5e/cup_plate/train \
  --val-dir data/ur5e/cup_plate/val --out runs/ur5e/cup_plate/baseline \
  --epochs 30 --seed 0
python -m physical_ai.bc --train-dir data/ur5e/cup_plate/train \
  --val-dir data/ur5e/cup_plate/val --out runs/ur5e/cup_plate/proprio \
  --epochs 30 --use-proprio --seed 0
```

Одна эпоха — один проход по обучающим данным. Значение `--epochs 30` задаёт
начальное число таких проходов. Наблюдайте за ошибкой на `train` и `val`, чтобы
понять, нужно ли продолжать обучение или менять модель. Скрипт сохраняет `best`
по наименьшей ошибке предсказания действий на `val`.

Теперь запустите BC в симуляторе:

```bash
python -m physical_ai.evaluate --robot ur5e --task cup_plate --kind bc \
  --checkpoint runs/ur5e/cup_plate/proprio/best.ts \
  --episodes 50 --seed 50000 --out runs/ur5e/cup_plate/bc_eval.json
```

Аналогично проверьте `baseline/best.ts`. Малая ошибка предсказания действий ещё
не означает, что робот хорошо выполняет задачу: небольшие ошибки могут накапливаться
во время движения. Поэтому основной результат — доля успешных эпизодов в симуляторе.

Проведите следующие сравнения:

- BC по изображению и BC с проприоцепцией на одинаковых данных.
- BC и RL-эксперт. Учтите, что эксперт получает точное состояние
  предметов, а BC должна ориентироваться по изображению.
- Обучение BC с проприоцепцией на 25% и на 100% демонстраций при
  одинаковых остальных настройках. Это **абляция объёма данных** — проверка,
  как один выбранный фактор влияет на результат. Отбирайте целые эпизоды.

Для каждого варианта достаточно одного обучения с одним seed, например `--seed 0`.
Повторять обучение с разными seeds не требуется. Это относится и к абляции объёма
данных: используйте один и тот же seed обучения для обоих объёмов.
Каждую сравниваемую модель оценивайте минимум на 50 эпизодах с одинаковыми
начальными условиями. Если используете эти результаты для выбора настроек,
итоговую оценку проведите на новых эпизодах, не использованных для подбора.

**Результат этапа:** две основные BC-модели для выбранной пары, таблица сравнения с RL
и абляция объёма данных. Покажите долю успехов и разберите несколько неудач по видео.
Вы можете менять архитектуру BC и способ обучения; требования к сдаваемому файлу
описаны в конце задания.

## 5. Проверьте устойчивость BC к изменениям сцены

До этого модели работали в исходных сценах. Теперь выясните, сохраняется ли их
качество, когда окружающая обстановка немного отличается. Это и есть проверка
**робастности**, или устойчивости модели.

Через [справочник MuJoCo](MUJOCO_GUIDE.md) и инспектор `physical_ai.scene_tools`
изучите доступные параметры объектов, материалов, физических свойств, камеры
и освещения. Выберите не менее трёх типов изменений для своих экспериментов.
Конкретные параметры и величину изменений определите самостоятельно.

Начинайте с одного изменения за раз. После каждой правки откройте сцену
и убедитесь, что задача сохранила смысл и робот всё ещё может её выполнить.
Не меняйте правила успеха. Затем можно исследовать сочетания изменений.

До экспериментов разделите варианты сцен на три группы: для обучения,
для выбора настроек и для итоговой локальной проверки. Последнюю группу
не используйте для подбора модели. Для выбранной пары оцените BC с проприоцепцией
на исходной сцене и на выбранных изменённых сценах. Сохраните одинаковое число
эпизодов и начальные условия при сравнении моделей.

**Результат этапа:** описание выбранных изменений, таблица успешности до и после
них и примеры ошибок. Объясните, какие изменения сильнее мешают модели и почему.

## 6. Обучите BC на изменённых сценах

Попробуйте повысить устойчивость, добавив разнообразие в обучающие данные.
Такие изменения обучающих примеров называют **аугментациями**.

Создайте JSON-файл со списком своих вариантов сцены. Формат одного варианта
показан в `configs/scene_example.json`, допустимые поля — в справочнике MuJoCo.
Передайте файл сборщику:

```bash
python -m physical_ai.data --robot ur5e --task cup_plate \
  --checkpoint runs/ppo/experts/ur5e/cup_plate/last.zip \
  --scene-bank configs/my_training_scenes.json \
  --out data/ur5e/cup_plate/augmented_train \
  --episodes 100 --seed 20000 --max-attempts 500
```

Сначала проверьте, что RL-эксперт успешно действует в новых сценах.
Если требуется его дообучение, выполните его и опишите в отчёте. Проверочные
данные соберите отдельно, на других seeds и вариантах сцены.

Изменение сцены требует новых действий эксперта. Например, нельзя передвинуть
объект в кадре и оставить старую запись действий как правильный ответ.
Преобразования самого изображения тоже допустимы, если правильное действие
не меняется. Флаг `--image-augmentation` в BC даёт простой пример изменения
яркости и добавления шума; он не заменяет обязательные эксперименты со сценой.

Обучите новый BC с проприоцепцией для выбранной пары, используя команды этапа 4
с новыми каталогами данных и результатов. Сравните его с прежним BC на исходных
и заранее отложенных изменённых сценах. Используйте одинаковое число демонстраций
для двух моделей. Если добавили больше данных, проведите ещё одно обучение
без аугментаций на таком же количестве данных: иначе нельзя понять, что помогло.

**Результат этапа:** BC-модель после обучения с аугментациями, результаты
сравнения и выводы. Улучшение не обязательно получится везде. Корректно проведённый
и объяснённый отрицательный результат тоже важен.

## 7. Подготовьте сдачу

Заполните [шаблон отчёта](REPORT_TEMPLATE.md). Скопируйте `submission.example.json`
в `submission.json`. В списке `models` должна быть одна запись: укажите выбранные
`robot` и `task` и пути к своим моделям. Пути считаются относительно каталога сдачи.

Для выбранной пары передайте:

- RL-модель: `last.zip` и соседний `last.json`;
- три BC-модели — baseline, с проприоцепцией, после обучения с аугментациями:
  для каждой `best.ts` и соседний `best.json`;
- данные LeRobot или доступные проверяющему ссылки на них;
- настройки, логи обучения, результаты оценки в JSON/CSV и несколько видео.

Также приложите код, команды воспроизведения и `REPORT.md`. Отчёт должен содержать
сравнения из этапов 2, 4, 5 и 6, а не только список запусков.

Проверяющий запустит модели выбранной пары на двух наборах: **base** — исходная
сцена с новыми начальными условиями; **advanced** — закрытые варианты этой сцены.
Точные изменения advanced не публикуются. Для подготовки используйте собственные
эксперименты с устойчивостью, а не результаты закрытой проверки.

### Если вы изменили архитектуру BC

Готовый тренер сам экспортирует модель в TorchScript (`.ts`). При своей архитектуре
сохраните тот же интерфейс: `forward(rgb, proprio)` возвращает четыре компоненты
действия для каждого примера. RGB — `float32[B,3,84,84]` в диапазоне [0,1];
проприоцепция — `float32[B,P]`, где P=16 для UR5e и P=18 для KUKA;
выход — `float32[B,4]` в диапазоне [-1,1]. B — число примеров в одном вызове.
Модель только по изображению тоже принимает `proprio`, но не использует его.
Если модель хранит состояние между шагами, добавьте экспортируемый `reset()`:
оценщик вызывает его перед новой попыткой.
